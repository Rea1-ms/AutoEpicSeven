# 资源同步与任务调度实现计划

这版准备把“领取资源、读取余额、调整等待、执行后回查每日”连起来。任务顺序仍只维护原调度表，不额外开启任务，不根据配置里的购买意图直接增加余额。本文记录本轮已实现的约定，离线验证结果见仓库验收记录；未进行实机购买、领取或战斗。

## 实现前的情况

资源栏读取后已经会更新面板，但不会重新安排竞技场和副本。商店、邮件会请求数据更新，宠物礼物还没有接入；数据更新完成也不会提前原先等待资源恢复的任务。现在竞技场、副本排在这些资源来源之前，后领取的资源容易等到下一轮才使用。

每日规划还有一处偏乐观的判断：另一个任务只要开启燃竭，就把该路线剩余每日档位都计入潜力，没有核实实际资源。此前记录的可执行次数也可能在补给后继续沿用。

## 一、先取得资源，再消费

只调整 `config_manual.py`（手动配置）的原优先级表，使用以下顺序：

重启 → 每日领奖 → 召唤 → 圣域日常 → 邮件 → 商店 → 宠物礼物 → 数据更新 → 竞技场 → 副本 → 圣域月常 → 骑士团 → 秘密商店 → 宠物 → 社区签到 → 限时活动 → 特殊活动。

这仍然只是已启用、已到期任务之间的顺序。商店或宠物还没到时间时照常跳过，不能为了预期资源提前购买或领取。后续骑士团、活动获得资源，也可以使用同一套同步入口，不需要再调整一套每日排序。手动工具继续独立。

## 二、领取后优先读取主页资源栏

| 来源 | 接入方式 |
| --- | --- |
| 商店 | 有可能改变资源的购买动作后标记待刷新；正常完成或部分成功后中止，都保留这个标记。购买次数只说明购买结果，不直接换算到账余额。 |
| 邮件 | 有领取动作后标记待刷新；空邮箱不产生请求。 |
| 宠物礼物 | 有领取动作后标记旗帜、体力待刷新，不预猜奖励种类和数量。 |
| 现有资源栏读取 | 成功读取后统一保存可信观察，并尝试处理对应的资源等待。 |

刷新意图在可能改变余额的动作前保存，避免操作后中断漏掉刷新；点击未生效最多产生一次额外读取，不直接增加资源。同一次任务里的多次购买或领取合并处理。任务安全返回无遮挡主页后，优先读取主页已有的旗帜、体力和天空石，不为此额外绕到副本、竞技场或装备背包。

读取失败时保留待刷新项，交给已启用的数据更新任务补读；连续请求合并，失败沿用有界重试和冷却。数据更新关闭时不强制开启，下次自然返回可读取页面时再处理，消费任务入场时仍会核对实际余额。

数据更新增加“仅补读待刷新资源”的路径。因补读提前执行时，保留原来完整巡查的到期时间；完整巡查本来已到期则照常执行，不能被轻量补读一直推迟。只清除本次可靠读到的字段，未读取字段继续保持待刷新。

## 三、明确哪些等待可以提前

竞技场和副本在安排下一次执行时，额外记录等待原因、所需资源、所需数量、配置依据以及当时写入的执行时间。

| 当前状态 | 新资源读到后的处理 |
| --- | --- |
| 因资源不足等待，且本轮条件已满足 | 提前到下一次正常调度；不打断正在执行的任务。 |
| 因资源不足等待，但仍不够下一批 | 重新计算自然恢复时间，只在能够提前时更新。 |
| 固定次数已用尽 | 保持原时间，不恢复次数；每日允许追加时仍走已有规划。 |
| 失败冷却、界面锁定或用户另设时间 | 保持原时间。 |
| 已有托管或扣费待确认 | 保留对应运行、结算时间和预留，不能重新启动。 |
| 任务关闭、路线不消费该资源 | 不安排执行。 |

判断门槛复用消费任务自身的规则：竞技场燃竭保留回满5面旗帜的等待策略；新到账不足5面时可以缩短等待，不必立刻开跑。副本按当前路线判断，服务器托管仍需要完整80体力单位，不能统一按“够打一场”处理。

不直接无条件调用任务。先确认等待记录里的执行时间仍与当前一致、配置未变，避免旧记录覆盖用户修改或后来的失败冷却。任务开始执行时结束这条资源等待，退出时按真实原因重新记录。

同一余额的重复读取不反复唤醒已到期任务；首次可靠读数、补给后读数和本地消费估算的纠正，也应能重新判断，不能只依赖“比上次文字识别数值更大”。

## 四、可信余额和每日进度分开保存

现有面板继续保存余额；另外保存实际观察时间、来源页面、资源版本、待刷新项和等待依据。本地扣费估算可以更新面板，但不能刷新“实际读到”的时间，也不能冒充新补给。

新增一个隐藏的资源运行状态组，挂在数据更新任务下，由各模块共用。它不依赖每日优先开关或数据更新任务是否开启。按配置文件和服务器隔离；语言或页面上下文变化后重新读取。旧配置没有等待记录时，先保留原执行时间，不能猜测旧等待原因。跨日保留实际资源与未决托管，不恢复已用次数，不清除未确认预留。

保存余额、观察版本和调度变化时使用现有批量写入方式。资源有效零值正常保存；读取失败保持未知，超过自然恢复上限的余额照常接受。

每日规划改用这份可信余额，只扣除尚未反映在这次余额中的有效预留；已扣款但未结算的记录不能再减一次。行动前仍在消费页面实读确认。旧的可执行容量随资源版本、路线配置、消费动作或观察过期而失效，不能在补给后继续沿用零容量。

未来潜力只计算实际资源、未用次数以及刷新前有限的自然恢复。商店购买配置只说明候选补给，不先计入可消费余额；宠物随机奖励在读到后才参与计算。快战和使用体力的托管共用同一份体力预算，按既有路线顺序分配，不能分别把同一余额算一遍。生命之叶单独核对，继续遵守已有使用设置，不扩大额度。费用未知或托管待确认时保持待核实，不把开启燃竭等同于所有档位都能完成。

资源增加只触发资源判断，不增加每日体力、挑战次数或活跃。竞技场完成战斗、快战实际完成后才回查每日；托管仍在结算确认后回查。托管期间独立完成的快战可以单独回查。回查一次领取当时全部可领奖励，不在本地直接算成完成。

每日满100并确认领奖后，停止为每日追加和回查；用户原定剩余次数、燃竭和资源同步继续按设置运行。

## 五、实施位置与顺序

1. **可信观察和等待依据。** 在 `tasks/base/`（任务基础目录）新增资源协调实现，接入 `resource_bar.py`（资源栏实现），并由竞技场、副本各自提供消费门槛和等待原因。先保留现有面板接口，避免全仓改名。
2. **获取后同步。** 接入商店、邮件、宠物礼物，补上数据更新的轻量刷新与合并请求；随后调整原调度表。资源刷新先完成，再让消费任务重新判断。
3. **每日预算。** 接入资源版本、预留和容量失效，修正燃竭未来潜力判断。继续使用现有固定次数账本与托管记录，不建立第二份消费次数账本。

隐藏状态只改配置定义源和任务组定义；生成文件由现有配置更新器产生，实施到该步骤时按项目约定取得运行授权。用户已批准并成功运行配置更新器，模板、参数与生成配置已同步；五种语言说明已补齐。

## 六、验收

离线回归沿用统一入口，覆盖资源同步、实际调度、每日规划、竞技场和副本相关集合；新增用例登记到现有清单。重点验证：

- 商店买到5面旗帜后，可靠读取到余额，原来等待自然恢复的燃竭竞技场提前执行；打完再回查每日。
- 宠物没有掉资源时不触发消费；随机得到旗帜或体力后只影响对应任务。体力不足80时不会重复启动托管。
- 商店部分购买成功后失败仍保留刷新；资源栏失败、局部字段成功、重复帧和同余额重复观察不会造出资源或反复开跑。
- 已关闭任务、固定次数已用尽、失败冷却、用户改时间和配置变化都不被旧资源等待覆盖；资源不够只缩短可提前的等待。
- 重启、跨日、语言切换、活跃托管和未决预留保持一致；快战扣费与托管结算仍分别回查，满100领奖后燃竭继续。
- 多来源刷新合并；轻量补读不推迟完整巡查，数据更新关闭时不被强制开启；原表仍是唯一执行顺序来源。

实机验收再使用实际购买、宠物领取和资源栏读数核对联动，分别观察“够用立即执行”和“不够用缩短等待”。随机奖励未出现时不宣称该分支已验证；本轮未进行实际购买或战斗。
